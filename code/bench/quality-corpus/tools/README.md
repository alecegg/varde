# Quality corpus tools

## Behaviour test convention

Each item contains at least two version files and one `behaviour_test.<ext>`. A `pair.json` declares two sides with `left` and `right`; otherwise a `versions` list in `manifest.toml` declares the versions, falling back to the item's source files for legacy six-version items. For each declared version, the runner copies it to a fresh temporary directory as `solution.<ext>`, copies the shared behaviour test next to it, builds it with the language's compile step where one exists, and executes the test against that solution. Every declared version must pass. A rich item may also declare optional preference versions named `alt-pipeline`, `alt-table`, and `alt-class` as pairs against `sensible` with `right_role` `alt-good`; they run through the same behaviour test. Python uses `python3`; TypeScript uses Node type stripping or `tsc`; Go uses `go test`; Rust uses an offline temporary Cargo crate; Java uses `javac` and `java`; C# uses `dotnet`; C++ uses `g++` or `clang++`. Missing toolchains are reported per version as `blocked`, and versions that fail their build step are reported as `broken`.

## Mutation self-check

`python tools/mutate_check.py --item <item-dir> --variant <file> --mutants <spec.toml>` replaces a throwaway mutation self-check: for each mutant it copies the item, applies one textual patch to the chosen variant, and runs the shared behaviour test through the same per-language commands as the behaviour runner. A mutant is `killed` when the behaviour test fails, `survived` when it passes, `broken` when the variant no longer compiles or syntax-checks, `unapplied` when its `find` text does not occur exactly once, and `equivalent` when the spec marks it so with a `reason` (equivalent mutants are counted and not run). A broken mutant is not a kill, because the test never ran; it is listed by id, and `allow_broken = true` on a spec entry accepts it. Survivors, broken, and unapplied patches are listed; the exit status is 0 only when every non-equivalent mutant is killed, 1 otherwise, and 2 for bad arguments or an unusable spec. `--jobs` (default 4) sets parallelism, `--timeout` (default 60) bounds each mutant, and `--json` prints one JSON object.

`--random-only` reruns the mutants behind the random-loop-alone switch that the spec's `[run]` table declares for the variant's language: `python = { env = "NAME" }` sets that variable to `1`, and `python = { command = [...] }` replaces the final run command with `{root}`, `{solution}`, and `{test}` substituted. A spec with no `[run]` entry for the language is a usage error. [mutants/order-quote.python.toml](mutants/order-quote.python.toml) is the template: 38 mutants and one equivalent against `items/python/b/order-quote/sensible.py`, every non-equivalent mutant killed, while `--random-only` leaves the 10 mutants that only the transcribed cases catch.

## Dataset-store export

`python tools/tiers.py --check` validates the category (b) task tier registry, item profiles, and restricted-store task names. Only rich-task padded comparisons count as padding evidence.


`export_pairs.py` writes one opaque `<pair_id>/` directory per pair. The current directory contract is provisional until the dataset-store package publishes its format; see [EXPORT_FORMAT.md](EXPORT_FORMAT.md). IDs derive from content digests, and manifest paths are relative. A pair whose right side is an `alt-good` preference version is exported with `role = "alt-good"` and `preference_neutral = true`, and never with a direction or label. `counts/count_items.py` reports the alt-good version count per rich task and language; it is report-only and not a gap.

## Item authoring specification

Run `python tools/item_spec_check.py --items <item-or-items-dir> --check` to print per-version metrics and structured violations for the six category (b) versions. Pass `--language` when the source extension does not identify the language.

`python tools/item_targets.py <item-dir> [--json]` prints one call's worth of authoring targets: whole-file tokens, function count, per-function tokens and rows, the allowed band for each variant still missing or out of band (measured by probing `item_spec_rules.py`'s rule functions, so the numbers cannot drift), and the checker's findings once all six variants exist. Alt version files present in the item are listed after the six variants with the same measurements and their sensible-like bands.

Optional alt versions (`alt-pipeline`, `alt-table`, `alt-class`) are declared in `pair.json` as `alt-good` pairs against `sensible`, and a `spec-profile.toml` `alts = ["alt-pipeline", ...]` list marks the ones the item requires. Absent alts are not findings. Each present alt is checked with the layered sensible limits (7-20 functions, 30-160 tokens, depth at most 4, entry fan-out at most 6) plus the common rules: the shared entry name and signature, no dead code, and no category words. Alts are exempt from comment parity and entry documentation parity, because a different style may document differently. An alt name outside the three known names is rejected with `unknown_alt`.

Unprofiled sensible variants use 2-6 functions, each 30-100 tokens, with one call level from the entry function. C++ allows 2-9 functions for this tier to accommodate its token-heavy data and result handling; the token and call-depth limits are unchanged. Layered sensible limits are language-independent and unaffected.

The opt-in `layered` profile (`spec-profile.toml`) sets language-independent limits for sensible, tiny, and namematched. Go accepts either `solution` or exported `Solution` as the shared entry name. Sensible uses 7-20 functions, 30-160 tokens per function, depth at most 4, and entry fan-out at most 6. Tiny and namematched use 28-72 functions, 5-90 tokens per function, at most 10 rows, entry fan-out 4-10, and chain depth 3-8; both require at least 3 forwarders.

Padded uses 14-22 functions, depth 3-6, and entry fan-out 4-10 when layered. Helpers allow 30-130 tokens, except Rust allows up to 160; entries have no upper token cap, except Rust allows up to 160. Unprofiled limits remain unchanged. Layered monolith whole-file tokens must be 0.8x-1.6x sensible; Rust monolith function tokens must exceed 75% of sensible function tokens, while other languages require them to exceed the sensible total. Layered sizematched allows a ±10% difference from sensible in whole-file and function tokens; unprofiled items retain ±3%.

The checker cannot confirm that every line executes, so reviewers and builders run each item's behaviour test under a coverage trace and report unexecuted lines per version. Use the language's own tool: Python `coverage` or `sys.settrace`; TypeScript `node --experimental-test-coverage` or `c8`; Go `go test -cover`; Rust `cargo-llvm-cov` when installed, otherwise reading; Java, C#, or C++ the language tool when available, otherwise reading. Only documented unreachable-by-domain error paths that the behaviour test also triggers may stay unexecuted.

The checker also flags unused declarations and Python locals, lines over 100 columns, non-opaque pair ids, and differences in the entry documentation or declaration form. Its small unused-symbol exemption table is in `item_spec_symbols.py`: Python allows `main`, `__all__`, and pytest setup hooks; TypeScript allows `main` and common test hooks; Java and C# allow `main` and setup/teardown hooks plus the `Item` harness wrapper, and C# also allows the `Solution` container the behaviour test calls into; C++ allows `main`, `std`, and setup/teardown hooks; Go allows `main`, `init`, and `TestMain`; Rust allows `main` and `test`. Add an exported API name only when the language requires it to be present without an in-file reference.

Same-file call graphs include calls through class members and receivers in Python, TypeScript, Rust, Go, Java, C#, and C++. Member calls count only when the target is an unambiguous same-file method; bare calls continue to respect local shadowing. Rust `Type::new()` calls reach a same-file `new` method. These edges feed dead-code reachability, call depth, and fan-out. Python construction also marks `__init__`/`__new__` and dunder lifecycle methods on that class as reachable.

## Repository split audit

`place_item.py --audit-repo` prints the audited root and exits non-zero when restricted data is inside the repository. It scans the files git would publish (tracked files plus untracked files that are not ignored, so installed dependencies and build output produce no findings), and without git it walks the tree skipping `.git`, `.venv`, `node_modules` and `__pycache__`. A finding is a test-split `.varde-split.json` marker, a path under a restricted task directory, a file under the quality corpus with a `labels/` ancestor or matching `*.label*`, `label*.json*`, or `*.labels`, a `panel-*.jsonl`, `human-*.jsonl`, or `batch-*.jsonl` file anywhere, or a file whose size and sha256 digest match a file in the restricted store, skipping files below 20 bytes. The digest scan catches a restricted file renamed inside the repository, while a restricted file whose name and content both differ from the store is only caught by the name and location rules. A missing restricted store is reported on stderr and the digest scan is skipped.

Category (b') pairs are keyed by pair id, not by a task id from `splits.lock`, so `--split locked` cannot route them. They are dev items written in place under `items/_bprime/<language>/<pair_id>/`.

Items may opt into layered limits with a `spec-profile.toml` containing `profile = "layered"`; items without this file retain existing limits (including sensible at 2-6 functions and depth at most 2, except C++ allows 2-9 functions). Layered sensible uses 7-20 functions, 30-160 tokens per function, depth at most 4, and entry fan-out at most 6. Layered tiny and namematched use 28-72 functions, 5-90 tokens per function, at most 10 rows, entry fan-out 4-10, chain depth 3-8, and at least 3 forwarders. Layered monolith whole-file tokens must be 0.8x-1.6x sensible; the default minimum is 1.3x with no upper bound. Layered sizematched allows ±10% in whole-file and function tokens; unprofiled items retain ±3%. Layered padded uses 14-22 functions, depth 3-6, and entry fan-out 4-10. Helpers allow 30-130 tokens, except Rust allows up to 160; entries have no upper token cap, except Rust allows up to 160. Layered padded may use a different call tree from tiny.
