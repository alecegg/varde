# Companion plan

Create one plan per category for action items from one review. Create a
category's plan lazily when its first action item is chosen. For a standalone
review, name each plan:

```text
  memory-bank/working/plans/<YYYY-MM-DD>-review-fixes-<target>-<category-lowercase>/plan.md
```

For a review nested inside a plan bundle, instead create:

```text
  memory-bank/working/plans/<plan-id>/<fix-id>/plan.md
```

Set `type: review-fix` and `source_review: <plan-id>/<review-id>` in that
plan's frontmatter. Keep its tasks and later child concepts inside the same
parent bundle. For a standalone review, retain the top-level path above.
Add every later action item from that category as another task in the same
plan. Do not create a plan for categories without action items. Pre-fill each
task with the finding title, location, summary, and selected solution as
acceptance criteria. Link the task from the finding block.

## Next steps for companion plans

After completion or archiving, tell the user what to do with each companion
plan. Nested companion plans are children of the originating plan and must
reach `completed` or `archived` before that parent plan can complete.

Tasks generated by the review fix process already have a chosen solution,
concrete acceptance criteria, and scope boundaries written during triage.
They do not need a planning session — invoke `/varde-build` against each
companion plan directly.

Only recommend `/varde-plan` first when a task is underspecified: the
acceptance criteria are vague, the solution was marked "discuss further", or
the task depends on a design decision that was explicitly deferred. If none of
those apply, building is the right next step.

Name each companion plan and its tasks in the closing output so the user has
a clear, actionable list.
